# Decision Log

Журнал ключових рішень. Активні відкриті питання — у `activeContext.md`.

## D-001 — Async-перший SQLAlchemy

- **Рішення:** усі DAO і таски використовують `AsyncSession`. Синхронний engine
  (`sync_sessin`) лишено тільки для викликів усередині `event.listen`-хуків
  (`SyncTaskService.match_task`).
- **Причина:** `Jira`/`Tempo` API повільні; async-IO дозволяє паралелити
  заван­таження без додаткових тредів.
- **Альтернативи:** повністю синхронний код (відкинули — не масштабується),
  threading (відкинули — складніше керувати сесіями SQLAlchemy).
- **Наслідки:** треба обережно з event-листенерами SQLAlchemy — там не можна
  робити `await`, тому `SyncTaskService` має окремий sync-шлях.

## D-002 — DTO через Pydantic v2

- **Рішення:** окремі DTO-моделі для кожного зовнішнього сервісу
  (`services/<name>/dto.py`), `Config.from_attributes = True`.
- **Причина:** валідація і нормалізація даних від зовнішніх API виконується
  до запису в БД; ID-валідатори `≤ 0 → None` дають uniform-нульові FK.
- **Альтернативи:** `dataclasses` (відкинули — нема валідації), словники
  (відкинули — нема типізації).

## D-003 — Локальний кеш ключів `JRProject` / `KeyTemplate`

- **Рішення:** `SyncTaskService` тримає класовий кеш зі `cache_ttl = 2 год`.
- **Причина:** `event.listen('set', ...)` на `TCEntry.description` викликається
  багато разів при пакетному імпорті — кожен SELECT був би надлишковим.
- **Наслідки:** після додавання нового `JRProject` через UI/SQL до 2 годин
  triggers можуть не бачити його. Обхід — рестарт або примусове скидання
  `SyncTaskService.cache_timestamp = None`.

## D-004 — `Computed` для `tc_entries.duration`

- **Рішення:** колонка `duration` оголошена як `Integer Computed("EXTRACT(EPOCH
  FROM end_at - start_at)")`.
- **Причина:** уникнути неконсистентності між фактичним інтервалом і збереженим
  `duration` (раніше це поле заповнював TimeCamp і воно іноді розходилося).
- **Наслідки:** при INSERT/UPDATE `duration` не передається з коду; будь-який
  міграційний рух Postgres-функції `EXTRACT` має зберігатись.

## D-005 — `BaseDAO._sync` видаляє відсутні моделі

- **Рішення:** `sync_all` — full-replace: моделі з БД, відсутні у вхідному
  DTO-списку, **видаляються**.
- **Причина:** для словникових сутностей (`JRProject`, `TCProject`) це
  природна повна синхронізація з джерелом.
- **Наслідки:** для worklog-ів і entries обов'язково використовувати
  `sync_all_between(...)`, який обмежує вибірку періодом. Не можна викликати
  `sync_all(db, [...])` із частковим списком worklog-ів — це знищить решту.

## D-006 — Стейт-машина статусів `WorklogSyncTask`

- **Рішення:** окрема таблиця `worklog_sync_tasks` із enum-статусами замість
  прямого створення worklog-у з entry.
- **Причина:** треба resumability — якщо `Tempo` API впав посеред пачки,
  можна продовжити з того самого статусу. Також стейт `pre_create → create`
  дозволяє підтягнути відсутні `JRIssue` окремим кроком.
- **Альтернативи:** робити все в одному виклику (відкинули — крихкість при
  частковому збої).
- **Зарезервовано:** `pre_update/update/updated/sync` — на майбутнє для
  оновлення вже синхронізованих worklog-ів (поки без реалізації).

## D-007 — `FastAPI` як майбутній HTTP-шар

- **Рішення:** залишити `fastapi` і `uvicorn` у залежностях, але не піднімати
  HTTP-сервер у v0.1.
- **Причина:** проект — single-user CLI/notebook. HTTP знадобиться, коли
  з'являться інші юзери або зовнішні триггери (cron, webhook).
- **Поточний обхід:** запуск через `main.py` або клітинки `main.ipynb`.

## D-008 — Typo `worllog` у назвах файлу і класу

- **Рішення:** залишити `src/tasks/worllog_sync_task.py` і клас `WorllogSyncTask`
  без перейменування.
- **Причина:** перейменування зачепить імпорти у `main.ipynb` та потенційно
  у скриптах оператора. Користі мало, ризик регресії — є.
- **Перегляд:** коли з'явиться окрема задача на cleanup — перейменувати разом
  із пошуком усіх `worllog` у репо (на 2026-05-11 знайдено лише цей файл).

## D-009 — Multi-user-ready схема API з самого початку

- **Рішення:** на етапі `add-rest-api` (фактично single-user) уже
  закладаємо таблицю `api_users` із `password_hash`, `worker_key`,
  `is_active` і кладемо `worker_key` у JWT claim. Жодних харкодів
  `current_user` на HTTP-шарі. `settings.current_user` лишається
  fallback-ом лише для CLI/notebook-сценаріїв.
- **Причина:** roadmap (див. `projectbrief.md`) передбачає масштаб
  4–100 користувачів на пізніших етапах. Перейти від «один користувач у
  `.env`» на таблицю користувачів пізніше — це міграція, переписаний
  auth і ламані контракти API. Зробити це одразу — майже безкоштовно.
- **Альтернативи:** *env-bcrypt single user* (відкинули — погана дорога
  на multi-user, рефакторинг неминучий). *OAuth/Keycloak* (відкинули —
  overkill і зараз, і пізніше для внутрішнього сервісу).
- **Наслідки:** першого користувача треба завести ручним `INSERT` із
  bcrypt-хешем; повноцінне керування користувачами піде окремою зміною
  `add-user-management-cli`. Per-user OAuth-токени на `Jira`/`TimeCamp`
  теж відкладаємо в окрему майбутню зміну.
- **Деталі реалізації:** D1 у
  [`design.md`](../../openspec/changes/add-rest-api/design.md) і
  `specs/api-auth/spec.md`.
- **Джерело:** діалог 2026-05-12 із підтвердженням roadmap (multi-user
  до 4–100 користувачів).
