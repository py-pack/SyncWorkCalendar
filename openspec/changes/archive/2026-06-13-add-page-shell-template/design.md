## Context

Дані-екрани зʼявлялися поетапно (`add-data-screens`, `extract-projects-screen`,
`rework-projects-screen`). Кожен зібраний з однакових цеглинок, але **без
спільного каркаса**: є лише `PageHeader.vue` (title+desc+`#actions`), решту
(`.page`-обгортка, банер `data-error`, `.page__body`) кожна в'юха дублює.

Звірені факти коду:
- `styles/shell.css` уже містить весь layout: `.page` (flex-колонка, повна
  висота), `.page__head`/`.page__titles`/`.page__actions` (верхівка), `.page__body`
  (скрол-контент). CSS переюзний — каркас лише обгортає його.
- `components/data/PageHeader.vue` — `title`, опц. `desc`, слот `#actions`.
- Спільний шаблон у 6 в'юхах:
  `.page` → `PageHeader[#actions]` → опц. суб-бар → `data-error` → `.page__body`.
- Суб-бар різний: `Tabs` (Projects), `.pipe` (Tempo), `.cal__chips` (Journal);
  у TimeCamp/Jira/Users його нема.
- `CalendarView` використовує власний `.cal`-layout (не `.page`) — інший каркас.

## Goals / Non-Goals

**Goals:**
- Один компонент `DataPage`, з якого складаються **всі** дані-/табличні екрани:
  заголовок + дії у верхньому правому куті + опційний тулбар + банер помилки +
  тіло.
- Прибрати копіпаст каркаса; уніфікувати рендер помилки й відступи.
- Нульова зміна поведінки наявних екранів (суто структурний рефактор).

**Non-Goals:**
- `CalendarView` — **не** під `DataPage` взагалі: це інший клас екрана
  (timesheet-grid), а не таблиця/список (D5).
- Без бекенду, контрактів API, схеми БД, нових залежностей.
- Без нової логіки (завантаження/синк/стор лишаються у в'юхах) — каркас суто
  презентаційний.
- Не вводимо узагальнену «таблицю-сторінку» з даними всередині — `DataTable`
  лишається окремим; `DataPage` лише обгортка-layout.

## Decisions

### D1 — Новий компонент `components/data/DataPage.vue`, що поглинає `PageHeader`

`DataPage` рендерить весь каркас: `.page` → верхівка (title/desc/`#actions`) →
опц. `#toolbar` → банер помилки → `.page__body` (дефолтний слот). `PageHeader`
**поглинається** в `DataPage` (його розмітка переїжджає всередину) і видаляється
як окремий публічний компонент — щоб не лишати два способи робити верхівку.

- **Альтернатива (лишити `PageHeader` як приватний під-компонент `DataPage`):**
  припустимо, але дає зайвий рівень; верхівка проста (кілька рядків) — інлайнимо
  в `DataPage`. Якщо десь верхівка потрібна без повного каркаса — повернемо
  окремий під-компонент тоді.

### D2 — API компонента: props + emit + 3 слоти

```
props:  title: string (required), desc?: string, error?: string | null
        tabs?: TabItem[]            — закладки (окремі під-сторінки); якщо задані —
                                      рендериться смуга закладок під заголовком
        activeTab?: string          — id активної закладки (TabItem.id)
emits:  update:activeTab (id: string)  — клік по закладці (v-model:active-tab)
slots:  #actions  — кнопки у верхньому правому куті (опційний)
        #toolbar  — додатковий суб-бар під заголовком/закладками: фільтри / pipe /
                    chips (опційний)
        default   — тіло сторінки (рендериться в .page__body)
```

- `#actions` рендериться лише якщо слот заданий (як зараз у `PageHeader`).
- `tabs` — якщо передано, `DataPage` рендерить смугу закладок (наявний компонент
  `Tabs`) між заголовком і `#toolbar`/тілом; клік емітить `update:activeTab`
  (підтримує `v-model:active-tab`). Якщо `tabs` не передано — смуга не
  рендериться. Деталі — D7.
- `#toolbar` — між закладками і тілом; туди в'юхи кладуть **не-табовий** суб-бар
  (`.pipe` у Tempo, chips у Journal). Може співіснувати із закладками. Якщо слота
  нема — нічого не рендериться.
- Тіло — дефолтний слот, всередині `.page__body` (скрол). В'юха кладе туди
  `DataTable`/дерево/`router-view` (для табів — активну під-сторінку).

### D3 — Банер помилки — prop `error`, рендериться каркасом

Замість того, щоб кожна в'юха писала `<p v-if="store.error" class="data-error">`,
`DataPage` приймає `:error="store.error"` і сам рендерить банер (з іконкою
`alert`), коли `error` не порожній. Уніфікує вигляд і прибирає копіпаст. Місце
банера — між тулбаром і тілом (як зараз).

- **Альтернатива (слот `#error`):** надлишково — банер усюди однаковий; prop
  простіший. Хто захоче кастом — додамо слот пізніше.

### D4 — Тулбар поза `.page__body` (не скролиться з контентом)

`#toolbar` рендериться **над** `.page__body`, тож суб-бар (Tabs/фільтри) лишається
закріпленим, а скролиться лише тіло — як у наявних екранах (Tabs/`pipe` зараз
поза `.page__body`). Це зберігає поточну поведінку 1:1.

### D5 — `CalendarView` — інший клас екрана, не під `DataPage` (остаточно)

Календар — це **не таблиця/список**, а тижневий timesheet-grid із власним
каркасом `.cal` (тулбар календаря, сітка днів/годин, блоки, поповери) — зовсім
інша історія. `DataPage` орієнтований **виключно** на табличні/списочні екрани,
тож календар під нього **не зводиться** — ні зараз, ні пізніше. Це не «відкладено
до окремої зміни», а свідома межа: спільного каркаса в цих двох типів екранів
немає.

### D6 — Рефактор — суто розмітковий, поведінка незмінна

Кожну з 6 в'юх переписуємо: зовнішній `.page`+`PageHeader`+error+`.page__body`
замінюємо на `<DataPage :title :desc :error>` зі слотами `#actions`/`#toolbar` і
тілом. **Уся логіка** (`onMounted`, стори, обчислення, обробники) лишається без
змін. Критерій приймання — `npm run build` чистий і візуально/функційно екрани
ті самі.

### D7 — Закладки = окремі під-сторінки; `DataPage` router-agnostic

Закладки (`tabs`) — це **окремі під-сторінки** одного екрана (як `ProjectsView`:
вкладки TimeCamp/Jira → routed під-в'юхи `/projects/timecamp`·`/projects/jira`).
`DataPage` **лише рендерить смугу закладок і емітить вибір** (`update:activeTab`);
**навігацію він не робить** — це лишається у в'юсі (`router.push`), а активна
під-сторінка показується в дефолтному слоті (`<router-view>` або умовний рендер).
Так каркас підтримує і **routed-таби** (Projects), і прості локально-станові
таби, не тягнучи залежність від `vue-router`.

- **Чому не вшивати роутер у `DataPage`:** прив'язка до `vue-router` зробила б
  каркас негнучким (локальні таби без маршруту стали б неможливі) і змішала б
  навігацію з презентацією. Контракт «рендер + подія» — мінімальний і покриває
  наявний патерн `ProjectsView` 1:1.
- **Лічильники закладок** — через `TabItem.count` (badge), як зараз; ліниві
  лічильники (тільки для завантаженого джерела) лишаються відповідальністю в'юхи.
- **`#toolbar` + `tabs` сумісні:** якщо екран має і закладки, і фільтри —
  закладки рендеряться першими, тулбар під ними.

## Risks / Trade-offs

- **[Регресія розмітки при рефакторі]** → Переносимо існуючий CSS-каркас 1:1
  (ті самі класи `.page*`); рефактор механічний, екран за екраном; `vue-tsc`
  ловить структурні помилки. Поведінка/стор не чіпаються.
- **[Видалення публічного `PageHeader`]** → Єдині споживачі — ці ж 6 в'юх (+
  можливо інші); усі переводяться в тій самій зміні. Grep підтверджує відсутність
  зовнішніх споживачів перед видаленням.
- **[Надмірна універсальність каркаса]** → Тримаємо мінімальний API (3 слоти +
  3 props); складніші екрани (Calendar) свідомо поза скоупом.

## Migration Plan

- **Frontend:** додати `DataPage.vue`; послідовно перевести 6 в'юх; поглинути/
  видалити `PageHeader`; `npm run build` має бути чистим. Розгортання — звичайний
  фронт-білд; rollback — ревертом коду. Бекенд не зачіпається.

## Open Questions

- Немає відкритих питань. `CalendarView` під `DataPage` **не зводиться** —
  це принципово інший тип екрана (тижневий timesheet-grid), а не таблиця/список;
  спільного каркаса в нього не буде (див. D5).
