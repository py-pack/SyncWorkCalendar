## Context

Задачі Jira потрапляють у локальну `jr_issues` лише двома шляхами (обидва — за
**ключами**): точковий `update_jira_issues(keys)` і побічно через `update_worklog`
(ключі з Tempo-worklog-ів періоду). Обидва кличуть `JiraService.search_issues(keys)`
→ JQL `key in (…)`. Тож задача без worklog-а в Tempo (і не передана явним ключем)
локально відсутня. Користувачу потрібно бачити **всі** задачі відстежуваних
проектів, включно з тими, де він не логав час, і «загальними» (не на нього
заасайненими).

Наявне в бекенді (вивчено в коді):

- `JiraService.search_issues(keys)` (`app/services/jira/jira_service.py:23`) —
  POST `api/2/search` із JQL `key in (…)`, **без пагінації** (`api/2/search`
  дефолтить ~50 результатів; решта губиться). Парсинг `issue → JiraIssueDTO` —
  у тому ж методі; у блоках `creator`/`reporter` помилково перевіряється
  `project_field` замість `creator_field`/`reporter_field` (тех-борг).
- `JRProjectDAO` зберігає проекти з прапором `is_watched`; `JRIssuesDAO.sync_by_key`
  робить **upsert** (`update_by_keys`, не full-replace) + автозаповнення `jr_users`/
  `jr_projects` із фактів.
- `routers/sync_triggers.py` — патерн sync-ендпоінтів: `_do_*` + `_execute(...)`
  обгортка (`run_job`, опційний `?background=true` → `202` + поллінг `GET /api-jobs`).

## Goals / Non-Goals

**Goals:**

- Тягнути **усі** задачі **відстежуваних** проектів (`is_watched`) у `jr_issues`,
  незалежно від наявності worklog-а й від assignee/reporter.
- Коректна **пагінація** Jira-пошуку (вибрати все, не лише першу сторінку).
- Запуск через явний sync-ендпоінт із логом у `api_jobs` і опційним фоном.
- Заразом полагодити баг парсингу `creator`/`reporter`.

**Non-Goals:**

- Редагування задач, round-trip у Tempo, синк за розкладом.
- Повний витяг **не**-watched проектів.
- Зміна екрана `/jira` (він уже читає з БД і підхопить нові рядки) і контракту
  `GET /jr-issues`.
- Зміна схеми БД / alembic-міграції.

## Decisions

### D1 — Витяг за JQL `project IN (…)` + період активності `updated`

Новий метод `UpdateJiraTask.update_issues_for_watched_projects(updated_from,
updated_to)` читає з БД ключі проектів із `is_watched = true` і тягне їхні задачі
одним JQL `project IN (KEY1, …) AND updated >= "from" AND updated <= "to 23:59"`.
**Період — за полем `updated`** (активність), не `created`: користувачу потрібні
задачі, **з якими працювали** у вікні, незалежно від дати створення (та сама
семантика, що у фільтра екрана `/jira`). Без періоду — усі задачі watched-проектів.
Скоуп — лише watched (рішення користувача).

*Альтернатива (відкинуто):* лишити тільки key-based — не вирішує проблему (потрібні
задачі без відомих ключів). Фільтр за `created` — відкинуто: ховав би старі активні
задачі (рішення користувача — `updated`).

### D2 — Пагінація обовʼязкова (`startAt`/`maxResults` цикл)

Новий шлях у `JiraService` (напр. `search_issues_by_jql(jql, *, page_size=100)`)
циклить POST `api/2/search` зі `startAt`/`maxResults`, акумулюючи `issues`, доки
зібрано `< total` (і доки сторінка не порожня — захист від нескінченного циклу).
Парсинг `issue → JiraIssueDTO` виноситься в спільний приватний хелпер, який
переюзовує і старий `search_issues(keys)`, і новий метод.

*Чому:* `api/2/search` без `maxResults` віддає лише ~50 — для проектів на сотні
задач повний витяг неможливий без пагінації.

### D3 — Upsert, не full-replace

Запис через наявний `JRIssuesDAO.sync_by_key` (→ `update_by_keys`, upsert + засів
`jr_users`/`jr_projects` із фактів). **Не** використовуємо `sync_all` (full-replace
видалив би задачі поза вибіркою). Навіть для повного витягу одного проекту
обмежуємось upsert-ом — безпечніше (не чіпає інші проекти й задачі поза сторінками).

*Чому:* консистентно з наявним `update_jira_issues`; нуль ризику видалити чуже.

### D4 — Без фільтра за worker_key / assignee / reporter

JQL — `project IN (…)` (+ `updated` за період), без `assignee`/`reporter`/
`worklogAuthor`. Тягнемо **усі** задачі проекту, включно з чужими (прямий запит
користувача).

### D5 — Ендпоінт `POST /sync/jira/issues-all` з опційним періодом, фон опційний

Додаємо `_do_jr_issues_all(payload)` + `POST /sync/jira/issues-all` за патерном
`routers/sync_triggers.py` (обгортка `_execute` → `run_job`, `?background=true`).
Тіло — **опційний** `PeriodBody { start, end }`: якщо задано, обмежує витяг полем
`updated` у вікні (D1); без тіла — усі задачі watched-проектів. Повертає лічильник
синкнутих задач (як інші `_do_*`).

*Чому:* фронт (попап) завжди передає період; опційність лишає шлях для CLI/повного
ре-синку. Повний витяг великого проекту може бути довгим → фон + поллінг
`GET /api-jobs/{id}`; лог у `api_jobs` — як решта синків.
*Альтернатива (відкинуто):* розширити `POST /sync/jira/issues` (key-based) — інша
семантика тіла; окремий ендпоінт чистіший.

### D6 — Фікс бага `creator`/`reporter` у спільному парсингу

Виносячи парсинг у спільний хелпер (D2), виправляємо умови: `creator` будувати при
`creator_field is not None`, `reporter` — при `reporter_field is not None` (замість
`project_field`). Покриває і старий key-based шлях.

### D7 — Фронтенд: **єдина** кнопка синку → попап із періодом

На `/jira` — **одна** кнопка синку, що відкриває попап `SyncIssuesModal` із
`PeriodPicker` → за підтвердженням `api.syncJrIssuesAll(period)` →
`POST /sync/jira/issues-all` з періодом → перезавантаження `loadJrIssues`.
**Period-синк worklog-ів із цього екрана прибрано** (`syncJrIssues` видалено):
користувач явно сказав, що йому потрібен один потік — витяг задач за вказаний період
(активність), без фільтра за користувачем. Дві окремі дії (period-worklog + повний
витяг) були помилкою — зведено в одну.

*Чому:* прямий фідбек користувача — «дві кнопки роблять окремо те, що треба разом».
Період береться з попапа (рішення користувача — попап, не тулбар-період).

## Risks / Trade-offs

- **Довгий витяг великих проектів (сотні-тисячі задач)** → опційний `background=true`
  + поллінг `api_jobs`; `page_size` помірний (напр. 100).
- **Навантаження/ліміти Jira API** → пагінація послідовна; запускається лише вручну,
  не авто (узгоджено з `data-pages-no-auto-sync`).
- **Некоректне завершення пагінації** → цикл спиняється і за досягненням `total`,
  і за порожньою сторінкою (подвійний захист).
- **`is_watched` не виставлено для проектів** → витяг нічого не дасть; UI підкаже
  (порожньо) — користувач спершу відмічає проекти на екрані «Проекти → Jira».
- **Поля задачі в `api/2/search`** (`creator`/`reporter`/`parent`/`customfield_*`)
  можуть бути відсутні в окремих задачах → парсинг має бути null-safe (фікс D6 саме
  про це).
