## Context

Екран `/jira` (`front/src/views/JiraView.vue`) показує задачі через
`GET /jr-issues` (плоский `list[JRIssueItem]`, `limit=50`), без пагінації й
фільтрів, а `onMounted` робить `loadIssues()` + `autoSyncIssues()` — фоновий
re-sync **усіх** відомих ключів задач (`POST /sync/jira/issues`) при кожному
відкритті. Задач багато (створювались роками), тож екран некерований.

Доступне в бекенді (вивчено наживо):

- `JRIssue` (`api/app/models/jr_issue.py`) має `created_at`
  (`DateTime(timezone=True)`, nullable, синкається з Jira) — є за чим фільтрувати
  період створення; **колонка вже існує**, міграція не потрібна (head
  `10b7dc50b00f`).
- `GET /jr-issues` (`routers/jr_issues.py` → `JRIssuesDAO.list_filtered`) уже
  підтримує `project_id`, `q` (ILIKE `key`/`name`), `limit` (кап 50). Похідне
  `active` — через `app/core/utils/issue_status.is_issue_active`.
- Jira-синк-тригери: `POST /sync/jira/projects` (`update_all_projects`),
  `POST /sync/jira/worklogs` (`PeriodBody`, потребує `worker_key`,
  `update_worklog`), `POST /sync/jira/issues` (`update_jira_issues(keys)`).
- Ноутбук `api/main.ipynb` (рядки 25–31) запускає синк Jira як
  `update_all_projects()` + `update_worklog(start, finish)`. `update_worklog`
  побічно тягне задачі за worklog-ами (`→ update_jira_issues`).
- `GET /tc-entries` (`routers/sync_status.py`) — готовий прецедент серверної
  пагінації `{ items, total }` + хелпери `_current_month()` / `_period_or_400()`.

Користувач підтвердив принцип (той самий, що для `/timecamp`, Memory Bank →
`data-pages-no-auto-sync`): екран читає **лише з локальної БД**; синк — **лише**
явною кнопкою з вибором періоду; авто-синк при відкритті прибрати. Окремо
підтверджено: фільтр статусу — **випадайка реальних статусів**; період створення —
дефолт **поточний місяць**.

`GET /jr-issues` має **двох** споживачів: екран `/jira` і select мапінгу
TimeCamp-проект → задача (`jrIssueSearch` у `components/projects/SyncSettingsModal.vue`).

## Goals / Non-Goals

**Goals:**

- Показати задачі Jira за обраний період **створення** (з локальної БД) із
  серверною пагінацією (`limit`/`offset` + `total`).
- Фільтри: проект (випадайка), статус (випадайка реальних статусів), пошук за
  назвою (`q`).
- Явна кнопка синку → попап із вибором періоду + швидкі шаблони; синк відтворює
  потік ноутбука (проекти + worklog-и за період).
- Прибрати авто-синк при відкритті екрана.
- Новий порядок колонок: **проект → тип → статус → номер → опис**.

**Non-Goals:**

- Ручне зіставлення untracked-записів із задачами; редагування задач; round-trip
  у Tempo.
- Перенесення патерну на `/tempo` (наступна окрема зміна).
- Синк за розкладом (майбутній етап roadmap).
- Будь-які зміни схеми БД / alembic-міграції.
- Фільтр стану синку / спільні `SyncState`/`SyncFilter` (див. D8 — на цьому екрані
  бінарного стану синку немає).

## Decisions

### D1 — Екран читає з локальної БД; синк лише явною кнопкою (без авто-синку)

`onMounted` більше **не** викликає `autoSyncIssues`. Екран вантажить дані лише
через `GET /jr-issues` (локальна БД). Синхронізація з Jira — тільки коли
користувач натискає кнопку й обирає період у попапі.

*Чому:* прямий запит користувача; узгоджується з `rework-timecamp-entries-screen`
(D1) і `rework-projects-screen` — фонові звернення до зовнішнього API на кожне
відкриття створюють зайве навантаження й шум `api_jobs`.
*Альтернатива (відкинуто):* лишити авто-синк + додати кнопку — суперечить
підтвердженому патерну.

### D2 — `GET /jr-issues` стає сторінкованим (BREAKING), select-споживач переводиться на `.items`

Відповідь `GET /jr-issues` змінюється з плоского `list[JRIssueItem]` на
`{ items, total }` (дзеркало `TCEntriesResponse`). Це **BREAKING** для контракту,
але контейнерно: єдиний інший споживач — `jrIssueSearch` (select мапінгу) —
просто читає `.items`.

*Чому:* `GET /jr-issues` **і є** ендпоінтом списку задач; вводити окремий
паралельний ендпоінт лише заради пагінації — дублювання. Проект уже робив свідомі
BREAKING-контракти так само (`GET /tc-projects` у `rework-projects-screen`).
*Альтернатива (відкинуто):* окремий `GET /jr-issues/page` поряд із плоским —
зайвий ендпоінт із майже тим самим SQL.

*Уточнення (рішення користувача при імплементації):* мапінг-select (`jrIssueSearch`)
має шукати серед **усіх** задач, а не лише цьогомісячних. Тож `jrIssueSearch` явно
передає широкий період (`updated_from='2000-01-01'`, `updated_to='2999-12-31'`) —
контракт ендпоінта не змінюється, лише споживач обирає широке вікно. Залишкове
обмеження: задачі з `NULL updated_at` у такий пошук не потраплять.

### D3 — Фільтри серверні: проект / статус / пошук / період створення

Усі фільтри застосовуються на боці сервера (бо пагінація серверна — клієнтський
фільтр бачив би лише поточну сторінку):

- `project_id` — фільтр за проектом (вже є).
- `status` — **точний** збіг із `jr_issues.status` (нове).
- `q` — ILIKE `key`/`name` (вже є).
- `updated_from`/`updated_to` — період за `updated_at` (активність, нове), дефолт
  ендпоінта — поточний місяць; екран `/jira` дефолтиться на поточний **рік** (D5).

*Чому:* консистентно з пагінацією; один прохід SQL із `WHERE` + `COUNT`.

*Уточнення (браузерний QA):* випадайка фільтра проекту наповнюється **лише
відстежуваними** проектами (`is_watched`) — фільтрувати за проектами, які не
синкаються, сенсу немає (їхні задачі локально й так майже відсутні).

### D4 — Випадайка статусів через facet-ендпоінт `GET /jr-issues/statuses`

Статуси в `jr_issues` — вільний текст із Jira (різні воркфлоу). Щоб наповнити
випадайку **повним** набором (а не лише статусами поточної сторінки), додаємо
легкий facet-ендпоінт `GET /jr-issues/statuses` (distinct, **усі** статуси —
завантажується один раз). Випадайка проекту натомість наповнюється наявним
`GET /jr-projects` (фронт уже тримає `jrProjects`).

*Чому:* за пагінації клієнт бачить лише сторінку, тож distinct-статуси треба з
сервера; окремий маленький ендпоінт простий і кешований.
*Альтернатива (відкинуто):* сегмент «Активні/Закриті/Усі» через `is_issue_active`
(без ендпоінта) — користувач явно обрав випадайку **реальних** статусів, не
бінарне активний/закритий.

### D5 — Період **активності** (`updated_at`): дефолт екрана «поточний рік», переюз `PeriodPicker`

Період фільтрує `GET /jr-issues` по **`updated_at`** (дата оновлення/активності, не
створення) — браузер задач має показувати те, **з чим працювали** у вікні,
незалежно від дати створення (рішення користувача після QA). **Дефолт ендпоінта**
(без параметрів) — поточний місяць (як на `/timecamp`, через `current_month`);
**екран `/jira`** дефолтиться на **поточний рік** (`defaultIssuePeriod`) і завжди
передає `updated_from`/`updated_to` явно. У тулбарі — той самий компактний
`components/data/PeriodPicker.vue` зі спільним набором `PERIOD_PRESETS`
(`lib/period.ts`); додано пресет «Цей рік». **Та сама `updated`-семантика
використовується й синком** (`add-jira-full-issue-pull`: JQL `updated` за період),
тож що на екрані, те й тягнеться з Jira.

*Чому:* користувач явно попросив період активності (`updated`), а не створення —
«синхронити те, з чим працював»; «поточний місяць» виявився завузьким дефолтом для
браузера задач, тож екран дефолтиться на рік. Переюз готового пікера й пресетів
прибирає дублювання. Валідація меж — `period_or_400` (`updated_from <= updated_to`,
інакше `400`).

### D6 — Синк = проекти + worklog-и за період (потік ноутбука 25–31)

Кнопка синку відкриває попап вибору періоду й послідовно викликає
`POST /sync/jira/projects`, потім `POST /sync/jira/worklogs` за обраний період —
точно як `update_all_projects()` + `update_worklog(start, finish)` у ноутбуці.
Задачі підтягуються як **побічний ефект** синку worklog-ів (`update_worklog →
update_jira_issues`). Додається клієнтський метод `syncJrWorklogs(period)`
(бекенд-ендпоінт уже існує); `syncJrProjects()` уже є. Попап — за патерном
`components/timecamp/SyncEntriesModal.vue`.

*Чому:* користувач прямо вказав на рядки 25–31 ноутбука як еталон синку Jira.
*Альтернатива (відкинуто):* окремий комбінований `POST /sync/jira` — нова ручка
заради двох уже наявних викликів; послідовний виклик із фронту простіший.
*Примітка:* `POST /sync/jira/worklogs` потребує `worker_key` у JWT — користувач
без `worker_key` дістане помилку синку (очікувано, задокументовано в Risks).

### D7 — Пагінація `{ items, total }`, сортування `updated_at` спадно

Дзеркалимо `GET /tc-entries`: `limit` (дефолт `50`, кап `200`), `offset` (дефолт
`0`), відповідь `{ items, total }`; `total` — окремий `COUNT` за тим самим
фільтром без `limit`/`offset`. Сортування — `updated_at DESC` (`NULL` останніми),
бо період і релевантність тут — за датою активності (оновлення).

*Чому:* задач багато; готовий перевірений патерн у проекті.

### D8 — Без `SyncState`/`SyncFilter`: екран Jira — браузер задач, не екран стану синку

На відміну від `/timecamp`, задача Jira **не має** бінарного стану синку з Tempo
(синкаються worklog-и, не задачі). Тож спільні `components/data/SyncState.vue` /
`SyncFilter.vue` тут **не застосовуються** — замість стану синку фільтри інші
(проект / статус / назва / період). Статус показується наявним `Badge`
(тон за статусом, як зараз).

*Чому:* нав'язати «мову синку» там, де бінарного синку немає, було б штучно.
Патерн «єдина мова синку» (`systemPatterns.md`) стосується екранів **зі станом
синку**; цей екран до них не належить.

### D9 — Переюз каркаса й примітивів; маленький `Select` на патерні поповера

Екран будується на наявному `DataPage` (`#actions` — кнопка синку; `#toolbar` —
фільтри зліва; тіло — `DataTable` + блок пагінації, як `/timecamp`). Попап синку —
`Sheet` (як `SyncEntriesModal`/`SyncSettingsModal`). Для випадайок проекту/статусу
додається невеликий переюзовний `Select`/dropdown на патерні поповера
`components/ui/Menu.vue` (click-outside + Esc), **без зовнішньої бібліотеки** (фронт
тримає лише `vue`/`vue-router`/`pinia`). Вибір проекту — з пошуком (як select
задачі у `SyncSettingsModal.vue`), бо проектів багато.

*Чому:* єдиний каркас екранів (`frontend-page-shell`) + цілісність дизайн-системи;
мінімум нового CSS і жодних залежностей.

## Risks / Trade-offs

- **BREAKING `GET /jr-issues` ламає select мапінгу** → переводимо `jrIssueSearch`
  на читання `.items` у тій самій зміні; перевіряємо `npm run build` (типи).
- **Синк за період** (кнопка) переведено на `add-jira-full-issue-pull`
  (`POST /sync/jira/issues-all`) — period-синк worklog-ів із цього екрана прибрано
  (інша семантика; деталі в тій зміні).
- **`updated_at` місцями nullable** → задачі без реального Jira-`updated_at` можуть
  не потрапити в період; сортуємо `NULL` останніми, фіксуємо як відоме обмеження.
- **Продуктивність `WHERE` + `COUNT` на великому обсязі** → серверна пагінація
  (`limit`/`offset`) + фільтр періоду обмежують вибірку; `jr_project_id` уже
  індексований. Фільтр `status` — без індексу (вільний текст), але звужений
  періодом.
- **Період за `updated_at` ховає неактивні задачі** → свідомий вибір користувача
  («показувати те, з чим працював»); дефолт екрана — поточний рік; період легко
  розширюється пресетами/ручними датами.
- **Дублювання хелперів періоду** (`_current_month`/`_period_or_400` у
  `routers/sync_status.py`) → переюзовуємо; за потреби виносимо у спільний модуль,
  щоб не копіпастити.
