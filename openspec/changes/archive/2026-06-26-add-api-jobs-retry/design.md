## Context

`api_jobs` — лог sync-операцій зі state machine
`running → needs_verification → verified` / `running → failed`. Кожен виклик
sync-тригера проходить через `app/api/jobs_wrapper.py` (`create_job`/`run_job`/
`run_existing_job`); HTTP-тригери живуть у `routers/sync_triggers.py`, де спільний
`_execute(...)` і набір work-factory `_do_*` (по одному на тригер). Шість тригерів
мають **Celery-таску** (`celery_tasks.py`: `sync.timecamp.*`, `sync.jira.*`,
`sync.jira.worklogs`, `sync.reconcile-links`), решта — **HTTP-онлі**
(`sync.jira.issues`, `sync.worklog-tasks.{prepare,resolve-issues,push-to-tempo,
push-one}`). Падіння (`failed`) видно в Журналі, але перезапустити конкретну
впавшу job-у з екрана не можна.

`add-api-jobs-cleanup` (щойно реалізована) додала `verify-all`/`summary`/retention,
але повтор лишила поза скоупом — саме його закриває ця зміна. Виконання ретраю —
**синхронне** (рішення користувача: кнопка чекає підсумок, як інші кнопки синку й
пер-рядковий push).

## Goals / Non-Goals

**Goals:**
- Пер-рядкова кнопка **«Перезапустити»** на `failed`-рядках Журналу, що повторює
  саме цю операцію її ж `trigger_name`+`payload`.
- Однаково запускати **і** Celery-, **і** HTTP-онлі тригери (спільний реєстр,
  реюз наявних `_do_*`).
- Кожен ретрай — **нова** `api_jobs`-джоба; стара `failed` лишається в історії.

**Non-Goals:**
- Зміни моделі/схеми БД, **без alembic** (head `69dde0d17ff2`).
- Редагування `payload` перед ретраєм; масовий «перезапустити всі»; ретрай
  не-`failed` джоб; background-режим (черга).
- «Мова синку» (`SyncState`/`SyncFilter`) — статус job-а 4-становий.

## Decisions

**D1. Ендпоінт `POST /api-jobs/{job_id}/retry`, лише для `failed`.**
Читає job-у за `job_id`; якщо її немає — `404`; якщо `status != failed` — `409`
(`"job is not in failed status"`). `failed`-only гарантує, що ретраємо лише те, що
впало (а не дублюємо `needs_verification`/`verified`/`running`). Маршрут вимагає
авторизації; `created_by` нової job-и = поточний користувач.
*Альтернатива* (ретрай будь-якого статусу) відкинута — повтор успішної/незавершеної
джоби збиває облік і плодить дублі.

**D2. Спільний реєстр `trigger_name → work-factory` (реюз `_do_*`).**
Вводимо мапу `TRIGGER_WORK: dict[str, Callable[[dict|None], Awaitable[dict]]]`, що
для кожного відомого `trigger_name` повертає корутину роботи від `payload`,
**перевикористовуючи** наявні `_do_*` зі `sync_triggers.py` (жодного дублювання
логіки синку). Тригери без `payload` (напр. `sync.timecamp.projects`) обгортаються
factory, що ігнорує `payload`. Для `sync.reconcile-links` наявного `_do_*` **немає**
(ендпоінт лише enqueue-ить Celery-таску), тож реєстр додає **inline**-factory, яка
синхронно кличе `ReconcileLinksTask().run(_lo(start), _hi(end), worker_key)` — той
самий код, що його гонить Celery-таска. Якщо `trigger_name` не в реєстрі →
`422 "trigger is not retryable"`.
*Розміщення (уникнути циклічного імпорту):* `sync_triggers.py` **не** імпортує
`api_jobs.py`, тож `api_jobs.py` може імпортувати реєстр зі `sync_triggers.py`
безпечно. Якщо цикл виникне — виносимо `_do_*`+реєстр у спільний
`app/api/sync_registry.py` (обидва роутери імпортують звідти). Дефолт — реєстр у
`sync_triggers.py` (де вже живуть `_do_*`), імпорт у `api_jobs.py`.

**D3. Виконання синхронне, з гарантованим поверненням нової job-и.**
Ретрай **не** використовує `run_job` напряму (той re-raise-ить виняток → `500`).
Натомість, за зразком синхронної гілки `_execute`/`_bg`: `create_job(running)` →
`try: result = await work(payload)` → на успіх `mark_needs_verification(result)`,
на виняток `mark_failed(str(exc))` (кожне — у власній сесії, як wrapper). Далі
**завжди** читаємо нову job-у за id і повертаємо `APIJobDetail` (HTTP `200`) — і
коли ретрай знову впав. Тобто синхронна невдача синку — це **не** `500`, а
`200` з новою `failed`-джобою (видно в Журналі). *Чому не `run_job`:* він зручний,
коли ендпоінт хоче re-raise, але тут потрібно віддати саме нову job-у в обох
випадках.

**D4. Стара `failed`-джоба не мутується.**
Ретрай створює **окрему** нову джобу; стара лишається `failed` в історії (аудит).
Звʼязку «retry_of» між ними **не** додаємо (без зміни схеми; D-Non-Goal). За
потреби трасування — у `payload` нової джоби лежать ті самі параметри, а час
відрізняє спроби.

**D5. Frontend — пер-рядкова кнопка, окрема від верхньої.**
У колонці дій `JournalView.vue` на рядку зі `status === 'failed'` додаємо кнопку
**«Перезапустити»** (`icon="sync"`), що кличе `store.retry(row.id)`. Верхня кнопка
«Підтвердити всі» (з `add-api-jobs-cleanup`) лишається без змін і ретраю **не**
запускає. Стор-дія `retry(id)`: `api.retryJob(id)` → далі `load()` (релоад
списку+зведення) і `refreshNeedsCount()` (новий стан міг додати
`needs_verification`). Помилку ретраю показуємо через банер `error` (як інші дії).
Кнопка `needs_verification`-рядка («Підтвердити») і клік-відкриття деталей —
без змін.

## Risks / Trade-offs

- **[Синхронний ретрай важкого тригера блокує запит 30–60с]** → Свідомо (рішення
  користувача); ретрай — точкова рідкісна дія по одному рядку, не масова. За
  потреби background — окрема майбутня зміна.
- **[Ретрай повторює ту саму помилку (баг не усунено)]** → Очікувано: нова job-а
  стане `failed` із тим самим `error` (тепер змістовним — після фіксу
  error-проброса в `jira_service`). Користувач бачить, що причина не зникла.
- **[`payload` старої джоби міг застаріти (напр. видалений `task_id` для
  push-one)]** → Робота сама поверне відповідний стан/помилку (напр. `404`-подібний
  результат у job.result/error); ретрай безпечний (іде через ту саму перевірену
  логіку `_do_*`).
- **[Циклічний імпорт `api_jobs ↔ sync_triggers`]** → `sync_triggers` не імпортує
  `api_jobs`; якщо зміниться — виносимо реєстр у `app/api/sync_registry.py` (D2).
- **[Реєстр розійдеться зі списком тригерів]** → Реєстр будується з тих самих
  `_do_*`, що й ендпоінти; невідомий тригер дає явний `422`, а не тихий збій.
