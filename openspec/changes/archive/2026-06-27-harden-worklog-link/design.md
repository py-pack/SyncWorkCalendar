## Context

Місток TimeCamp↔Tempo уже існує у `worklog_sync_tasks`:

```
tc_entries.id ◀──(WST.source_id, NOT NULL, index)── WST ──(WST.target_id, nullable, index)──▶ jr_worklogs.id
```

Підтверджено в коді: `WorklogSyncTask.source_id == TCEntry.id`,
`WorklogSyncTask.target_id == JRWorklog.id` (= Tempo `originId`). Але це **мʼякі**
лінки — без FK і без `UNIQUE`. Дедуп `JRWorklogDAO.find_match` не довіряє їм, а
матчить кортеж `(jr_issues_id, jr_worker_key, started_at, duration)`. Через це
можливі: дангл-`target_id` (на видалений worklog), кілька WST на один `source_id`,
орфан-дублі в Tempo (worklog без WST).

**Критична особливість:** і `tc_entries`, і `jr_worklogs` — **дзеркала** зовнішніх
систем; `BaseDAO._sync`/`sync_all_between` **видаляють** локальні рядки, відсутні у
свіжому пулі. Тож будь-які FK мають коректно співіснувати з цими видаленнями.

## Goals / Non-Goals

**Goals:**

- Зробити місток **явним і забезпеченим БД**: один WST на запис, лінки без
  дангл-посилань.
- Перевести дедуп на **довіру до лінку** (кортеж — fallback).
- Підготувати ґрунт для надійної чистки дублів (`add-worklog-dedup-cleanup`).

**Non-Goals:**

- Прямий FK у `jr_worklogs → tc_entries` (відхилено: `jr_worklogs` — дзеркало,
  колонку довелося б ре-стемпити після кожного пулу; дублює `WST.source_id`).
- Зміна самої схеми синку/реконсиляції (upsert-by-`source_id` лишається; ми лише
  **забезпечуємо** констрейнтами те, що вже припускається).
- Видалення/редагування worklog-ів — окремі зміни.

## Decisions

### D1. `UNIQUE(source_id)` на WST — ядро інваріанту

Один місток на один TimeCamp-запис. Сьогодні це лише припущення
`create_task_for_sync`/`get_match_candidates` (upsert за `source_id`); робимо його
**DB-констрейнтом**. Перед накладанням — нормалізація (D5): з кожної групи WST за
`source_id` лишаємо один (пріоритет: із `target_id` і просунутим `status`), решту
видаляємо.

### D2. FK `target_id → jr_worklogs.id` `ON DELETE SET NULL`

Коли worklog зникає з Tempo (легітимне видалення або чистка дублів), посилання
**занулюється**, а не дангліт. Це безпосередньо обслуговує
`add-worklog-dedup-cleanup`: видалення зайвого worklog-а само очищає лінк (а наша
чистка спершу **перенацілює** `target_id` на залишений, тож SET NULL — лише
страхувальна сітка).

**Взаємодія з re-sync (ризик і чому прийнятно):** пул worklog-ів повертає **всі**
worklog-и worker-а за період; відсутній у пулі worklog справді зник із Tempo, тож
локальне видалення + `SET NULL` — **коректні**. Псевдо-видалення можливе лише при
частковому збої пулу (помилка, не норма). Важливо: WST зі `status = created` і
зануленим `target_id` **не** ре-пушиться (реконсиляція обробляє лише
`create`/`pre_update`, а `pre_update` потребує `target_id`), тож занулення не плодить
нових дублів. Лишається відновлюваним наступним матчем/чисткою.

### D3. `source_id` — лише `UNIQUE`, **без hard-FK** (рішення користувача)

На `source_id` накладаємо тільки `UNIQUE` (D1) — **без** FK на `tc_entries`. Причини
(рішення користувача):

- TimeCamp і Tempo — **різні сервіси**; ми синхронимо їх **за можливості**, але
  локальну історію WST **не чіпаємо** автоматично, крім випадків, коли вона
  **некоректна** (саме наш кейс — задвоєння). Каскадне видалення WST разом із
  зниклим TimeCamp-записом цьому суперечить (стерло б історію).
- `ON DELETE CASCADE` тут небажаний; `RESTRICT`/`NO ACTION` зламали б re-sync
  `tc_entries`; `SET NULL` неможливий (`source_id NOT NULL`). Тож для source —
  **жодного** delete-FK; цілісність картки забезпечує `UNIQUE`, а посилання на
  `tc_entries` лишається на app-рівні (як і було).
- **Бонус:** прибирає головний ризик (CASCADE × звужений re-sync entries) повністю.

Явне видалення осиротілих/застарілих WST за потреби — **пізніше й іншими способами**
(окрема ручна/планова чистка), а не FK-каскадом.

### D4. Дедуп довіряє лінку, кортеж — fallback

`find_match`-шлях: якщо WST уже має `target_id` (лінкований) — він **не** кандидат на
повторний пуш (це вже діє через `status`). Для **виявлення дублів** і вибору
«канонічного» worklog-а в групі — worklog із наявним `WST.target_id` є джерелом
правди (його лишаємо), а кортеж лише групує. Тобто `(issue, worker, started_at,
duration)` лишається механізмом **виявлення** орфанів, а явний лінк — механізмом
**ідентифікації канонічного**. Це й використає `add-worklog-dedup-cleanup` (D2 там).

### D5. Міграція: спершу нормалізувати дані, потім констрейнти

Порядок ревізії (іначе констрейнти впадуть на наявних порушеннях):

1. **Дедуп WST за `source_id`:** для кожної групи лишити один (із `target_id` і
   найбільш просунутим `status`), решту `DELETE`. Це **єдине** видалення WST у
   міграції — чистимо саме некоректну (задвоєну) історію, як просив користувач.
2. **Занулити дангл-`target_id`:** `UPDATE worklog_sync_tasks SET target_id = NULL
   WHERE target_id IS NOT NULL AND target_id NOT IN (SELECT id FROM jr_worklogs)`
   (потрібно, щоб FK `target_id` накладався).
3. `CREATE UNIQUE INDEX` на `source_id`; `ADD CONSTRAINT FK target_id → jr_worklogs
   … SET NULL`. **На `source_id` FK не накладаємо** (D3) — осиротілі за `source_id`
   WST **лишаються** (історію не чіпаємо).

`downgrade` — дзеркальне зняття констрейнтів (data-fix незворотний, але це чистка
саме некоректних дублів).

## Risks / Trade-offs

- **[Міграція видаляє задвоєні WST]** Лишається один WST на `source_id`, решта
  дублів зникає. → Це і є мета (чистимо саме некоректну історію); лічильник видалень
  залогувати. Осиротілі за `source_id` WST **не** чіпаємо.
- **[SET NULL «забуває» лінк при хибному видаленні дзеркала]** → Не ре-пушиться
  (status-гард), відновлюється матчем; пул повертає повний період.
- **[`source_id` без FK → можливі WST на зниклий entry]** Свідомий компроміс
  (історію не чіпаємо). `UNIQUE` тримає кардинальність містка; явну чистку сиріт —
  пізніше окремими способами.
- **[Велика таблиця — час міграції]** Data-fix + індекс на проді. → Запити прості
  (по `source_id`/`target_id`), обсяг помірний.
