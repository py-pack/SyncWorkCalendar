## Context

Екран «Проекти» зʼявився у зміні `extract-projects-screen` (заархівовано
2026-06-13). Під-вʼюха TimeCamp успадкувала з тих часів: інлайн-тогл `is_sync`,
плоский список, авто-синк при відкритті (D4 тієї зміни) і period-based
`GET /tc-projects` (`entries_count` за період). На практиці це дало три болі:
**(1)** 6 HTTP-запитів на відкриття (2 GET даних + 2 POST синку + 2 GET reload);
**(2)** проекти TimeCamp — насправді дерево (`tc_projects.parent_id`) з кольорами
(`tc_projects.color`), які ніяк не показані; **(3)** інлайн-тогл легко вимкнути
випадково, а маппінг показує лише сирий `issue_key`.

Поточні факти коду (звірено):
- `tc_projects` уже має `parent_id`, `color`, `level`, `is_archived`, `is_sync`,
  `issue_key` — **міграція не потрібна**.
- `jr_issues` має `key`, `name`, `status` (вільний рядок) — назва й статус
  задачі доступні локально.
- `GET /tc-projects` (роутер) рахує `entries_count` через subquery по
  `tc_entries.start_at` між `start`/`end`; саме це тримає date-параметри.
- `autoSyncProjects()` у `stores/tables.ts` — джерело зайвих POST + повторного
  GET; `loadProjects()` тягне обидва джерела (tc+jr) одним набором.
- Єдиний споживач `GET /tc-projects` — цей фронт, тож BREAKING-зміна контракту
  безпечна в межах монорепо.

## Goals / Non-Goals

**Goals:**
- **Одна під-вʼюха = один data-запит.** Відкриття `/projects/timecamp` робить
  **лише `GET /tc-projects`**; `GET /jr-projects` вантажиться **тільки** при
  переході на вкладку Jira. Жодних авто-POST. On-demand «словники» (пошук задач
  у попапі) — дозволені.
- Древовидний рендер TimeCamp-проектів з кольоровим акцентом і тьмяними архівними
  вузлами.
- Безпечне керування синком через **попап** (а не інлайн-тогл): увімкнути синк
  можна лише разом з обраною задачею.
- Маппінг показує **назву** Jira-задачі (а не лише ключ), тінтовану кольором
  проекту; закриті задачі — тьмяні.
- Синк проектів — **окрема явна кнопка**, ніколи не автоматично.

**Non-Goals:**
- Під-вʼюха Jira-проектів не змінюється (лишається `is_watched`-тогл).
- Без змін у sync-рушії, моделях, схемі БД (нема alembic-ревізії).
- Без RBAC, без редагування дерева (drag/reorder), без створення/видалення
  проектів — лише читання структури + локальні прапори `is_sync`/`issue_key`.
- Без серверної пагінації Jira-задач поза простим `limit` для select-а.

## Decisions

### D1 — `GET /tc-projects` без date-фільтра; `entries_count` прибрано

Параметри `start`/`end` і поле `entries_count` видаляються. Проекти — статична
довідкова структура, не залежить від періоду; per-period лічильник entries —
зайва причина date-фільтра і частина «6 запитів».

- **Альтернатива (all-time COUNT):** лишити `entries_count` як загальний підрахунок
  без періоду. Відкинуто за рішенням користувача — колонка зайва на екрані
  конфігурації (дерево + маппінг + синк).

### D2 — Резолв назви/активності маппінгу в `GET /tc-projects` (LEFT JOIN)

Замість того, щоб фронт окремо тягнув усі задачі й мапив `issue_key → name`,
бекенд резолвить це **одним LEFT JOIN** `jr_issues ON tc_projects.issue_key =
jr_issues.key` і віддає `issue_name` (`str | null`) та `issue_active`
(`bool | null`). `null` — коли проект не змаплено або ключ не знайдено в локальній
БД.

- **Чому на беку:** тег задачі видно у кожному рядку дерева; клієнтський резолв
  вимагав би завантажити **всі** задачі (їх «дофіга»), що суперечить меті
  «не тягнути все підряд».
- **Soft-link, не FK:** звʼязок за рядком-ключем (як у календарі WST). Якщо задача
  ще не синкнута локально — `issue_name = null`, тег показує лише ключ.

### D3 — «Активність» Jira-задачі = статус не в «done»-сеті (похідний прапор)

`JRIssue.status` — вільний рядок (локалізований, кастомні воркфлоу). Вводимо
**один хелпер** `is_issue_active(status) -> bool`, що звіряє статус (case-insensitive,
trim) із константним сетом «завершених»: `done`, `closed`, `resolved`,
`cancelled`/`canceled`, `won't do`, `готово`, `закрито`, `виконано`,
`скасовано`, `вирішено`. `issue_active = status ∉ done-set`. Цей самий хелпер
використовують обидва endpoint-и (`/tc-projects.issue_active`,
`/jr-issues.active`).

- **Ризик локалізації:** сет неповний для екзотичних воркфлоу → деякі закриті
  задачі лишаться «активними». Прийнятно для v1: прапор лише візуальний (тьмяність),
  не блокує дій. Сет винесено в одну константу для легкого розширення.
- **Альтернатива (status category з Jira):** Jira має `statusCategory`
  (`done`/`indeterminate`/`new`), але `jr_issues` його **не зберігає** — додавати
  колонку = міграція + зміни синку. Відкладено; рядковий сет дешевший і без міграції.

### D4 — Фільтр за станом синку (`is_sync`) + швидкий пошук — клієнтські

**Уточнено за фідбеком користувача (2026-06-13):** фільтр під-вʼюхи TimeCamp
працює **за `is_sync`** (а не за `is_archived`), бо на екрані конфігурації
синку найкорисніше бачити «що вже в синку / що ні»; фільтр за архівністю давав
порожні/однакові вибірки (у БД майже всі проекти не архівні). Значення:
`усі | у синку | не в синку` (`у синку` → `is_sync = true`; `не в синку` →
`is_sync = false`; `усі` → без фільтра).

Фільтр і **швидкий пошук** (по `name`/`issue_key`/`issue_name`, case-insensitive)
застосовуються **на клієнті** по вже завантаженому списку — **без re-fetch**
(перемикання фільтра / ввід у пошук = 0 запитів). Це навіть краще лягає на
принцип «одна сторінка = один запит»: початкове відкриття — один `GET
/tc-projects` (усі проекти), далі фільтрація/пошук локальні.

- **Сирітки при фільтрі:** якщо видимий вузол має відфільтрованого батька, фронт
  **піднімає** його в корінь (orphan-hoisting у `buildTree`), щоб нічого не
  зникло. Архівні проекти **завжди показані** (лише тьмяні) — від фільтра синку
  не залежать.
- **Бекендний `active`(`is_archived`) param лишається** опційною можливістю API
  (`api-tc-projects-management`, дефолт `all`), але проектний UI його **не
  використовує** — вантажить усе і фільтрує локально. Зберігаємо як корисний
  серверний фільтр на майбутнє; видаляти контракт заради цього не варто.

### D5 — Дерево будується на фронті з плаского списку

Бекенд віддає плаский список з `id`/`parent_id`; фронт будує дерево
(`lib/tree.ts`: `buildTree(items)` → корені + `children[]`, orphan-hoisting,
стабільне сортування за `name`). Рендер — рекурсивний, з відступом за глибиною.

- **Чому не на беку:** дерево потрібне лише для UI; плаский контракт простіший і
  переюзний. Глибина TimeCamp-дерева мала (десятки-сотні вузлів) — рекурсія на
  клієнті дешева.

### D6 — Колір: тінт тега задачі + акцент вузла; архівні тьмяні

`tc_project.color` (hex із TimeCamp) застосовується як: **(а)** акцент вузла
дерева (ліва смужка/крапка), **(б)** тінт тега змапованої задачі (фон/бордер
тега). Архівні проекти (`is_archived`) — приглушений колір + знижена
непрозорість. Тег **закритої** задачі (`issue_active=false`) — сірий+напівпрозорий
незалежно від кольору проекту.

- **Безпека кольору:** значення з зовнішнього API; застосовуємо лише як CSS-змінну
  для кольору/бордера (не innerHTML), валідовуючи на `^#?[0-9a-fA-F]{3,8}$`; інакше
  фолбек на нейтральний токен.

### D7 — Попап замість інлайн-тогла; правило збереження

Інлайн-`is_sync`-тогл прибрано (ризик випадкового кліку). Налаштування синку — у
модалці, що відкривається кнопкою-шестернею **або подвійним кліком** по рядку.
Модалка: тогл «увімкнути синк» + select задачі з пошуком. Правило:
- Синк **увімкнено** + задачу **не обрано** → **Save disabled**.
- Синк **увімкнено** + задачу обрано → Save → `PATCH {is_sync:true, issue_key}`.
- Синк **вимкнено** → Save дозволено; шлемо `PATCH {is_sync:false}`, наявний
  `issue_key` **зберігається** (просто не синкаємо).

### D8 — Select задачі з пошуком: `GET /jr-issues?q=&limit=10`

Задач багато, тож select не тягне всі: на ввід (debounce) шле
`GET /jr-issues?q=<text>&limit=10`. Пошук — case-insensitive `ILIKE %q%` по
`key` **або** `name`; сортування `updated_at DESC` («останні 10 відповідно до
пошуку»); `limit` капується (≤50). Закриті задачі (`active=false`) у списку —
тьмяні.

- **Резолв обраного/наявного ключа:** назва вже-змапованої задачі приходить у
  `GET /tc-projects.issue_name`, тож попап показує її одразу без окремого запиту.

### D9 — Прибрати авто-синк; синк — окрема явна кнопка (кожен сервіс)

`autoSyncProjects()` і вся логіка «вікна свіжості» для проектів видаляються. У
шапці зʼявляється кнопка **«Синхронізувати проекти»** → `syncProjects()`, що
спрацьовує **тільки** на клік — ніколи автоматично. Кнопка запускає синк
**для кожного сервісу незалежно** (`POST /sync/timecamp/projects` **і**
`POST /sync/jira/projects` через `Promise.allSettled` — збій одного сервісу не
блокує інший), потім reload завантажених під-вʼюх. Помилка будь-якого сервісу
показується банером і повертає кнопку в стан помилки (не «done»).

### D10 — Лінива загрузка по під-вʼюхах (одна сторінка = один запит)

Дані вантажить **кожна під-вʼюха сама** при відкритті, а не батьківський
`ProjectsView` одразу за обидві:
- `views/projects/TcProjects.vue` на `onMounted` → `loadTcProjects(active)`
  (лише `GET /tc-projects`).
- `views/projects/JrProjects.vue` на `onMounted` → `loadJrProjects()`
  (лише `GET /jr-projects`) — тобто Jira-проекти тягнуться **лише** коли
  користувач переходить на вкладку Jira.
- `ProjectsView.vue` **не вантажить дані** на mount (тільки каркас + таби +
  кнопка синку).
- Кожен loader **ідемпотентний** (guard за «вже завантажено»), щоб перемикання
  туди-сюди між вкладками не пере-запитувало без потреби.

**Наслідок — лічильники вкладок ліниві:** badge вкладки показує `length` лише
**завантаженого** джерела; невідвідана вкладка не має лічильника, доки на неї не
перейдуть (прийнятно — узгоджено з користувачем «коли перейдемо на Jira, тоді й
підвантажимо Jira-проекти»).

- **Альтернатива (eager-load обох):** простіші лічильники вкладок одразу, але
  два запити на відкриття однієї сторінки. Відкинуто — порушує принцип «одна
  сторінка = один запит даних».

## Risks / Trade-offs

- **[BREAKING контракт `/tc-projects`]** → Єдиний споживач — цей фронт; типи
  (`api/types.ts`), клієнт і стор оновлюються в тій самій зміні. Зовнішніх
  інтеграцій нема.
- **[Неповний done-сет статусів (D3)]** → Прапор лише візуальний; сет — одна
  константа, легко доповнити. Документуємо як відоме обмеження.
- **[Soft-link `issue_key → jr_issues.key` (D2)]** → Якщо задача не синкнута
  локально, `issue_name=null` і тег показує лише ключ; кнопка явного синку
  проектів/задач закриває прогалину. Узгоджено з підходом календаря.
- **[Колір із зовнішнього API (D6)]** → Валідуємо hex регексом і застосовуємо лише
  через CSS-змінну; невалідне значення → нейтральний фолбек (без XSS-вектора).
- **[Сирітки при фільтрі active (D4)]** → Orphan-hoisting у `buildTree` гарантує,
  що активний вузол з архівним батьком не зникне.

## Migration Plan

- **Backend:** правка двох роутерів + двох схем + DAO; **без alembic-ревізії**
  (head лишається `10b7dc50b00f`). Розгортання — звичайний деплой API; rollback —
  ревертом коду.
- **Frontend:** оновити типи/клієнт/стор/в'юхи синхронно з API; `npm run build`
  (`vue-tsc` + `vite`) має бути чистим. Розгортання — звичайний фронт-білд.
- **Сумісність:** бек і фронт деплояться разом (контракт `/tc-projects`
  змінюється). Проміжного стану зі старим фронтом + новим беком не підтримуємо
  (внутрішній інструмент, один реліз).
